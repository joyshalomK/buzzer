# FM Family Quiz Buzzer

대한가정의학과의사회 가족 송년모임용 실시간 퀴즈 부저 시스템입니다.
참가자는 QR 코드로 접속해 닉네임만 입력하면 되고(앱 설치·회원가입 없음), 사회자가 부저를 열면 **서버(PostgreSQL)가 가장 먼저 접수한 1명**만 승자로 확정합니다.

| 경로 | 사용자 | 설명 |
| --- | --- | --- |
| `/join`, `/room/:roomCode` | 참가자 (모바일) | 닉네임 입장 → 부저 |
| `/admin` | 사회자 (데스크톱/태블릿) | 비밀번호 로그인 후 진행 |
| `/display`, `/display/:roomCode` | 대형 스크린 | 읽기 전용, 인증 불필요 |

게임 모드는 네 가지이며 사회자 화면에서 전환합니다. 참가자 화면과 대형 스크린은 자동으로 따라 바뀝니다.
- **일반 퀴즈 부저** — 가장 먼저 누른 1명 (1~7장)
- **FAMILY SYNC MODE** — 가족 2명이 10초 안에 "최대한 같은 순간"에 누르기 (8장)
- **가족 이구동성 (FAMILY MATCH)** — 가족 2명이 A/B 중 같은 답을 고르면 1점, 최대 10문항 누적 순위 (9장)
- **OX SURVIVAL** — 사회자가 말로 문제를 내고 전원이 O/X, 틀리면 탈락, 최후의 1인 우승 (10장)

## 1. 기술 설계 요약

**스택**: React 19 + Vite + TypeScript, Tailwind CSS v4, Supabase(PostgreSQL + Realtime), Vercel, Web Audio API, `qrcode`.

### 핵심 결정

1. **별도 API 서버 없음 — 모든 쓰기는 PostgreSQL RPC(`SECURITY DEFINER` 함수)로만.**
   브라우저는 공개용 anon 키만 갖고, 테이블에 직접 쓰기 권한이 전혀 없습니다. 함수 내부에서 토큰을 검증합니다. Edge Function/서버리스 함수가 필요 없어 구성 요소가 최소화됩니다.
2. **승자 판정 = 조건부 UPDATE 1문장** (`supabase/migrations/…_buzzer.sql`의 `public.buzz`)
   ```sql
   update rounds set status='LOCKED', winner_id=…, winner_at=clock_timestamp()
   where id = $round and status = 'ARMED' and winner_id is null and arm_seq = $arm
   ```
   동시 요청은 행 잠금으로 직렬화되고, 먼저 커밋된 요청 이후의 요청은 WHERE 조건을 다시 평가해 0행이 됩니다. 추가로 `buzz_attempts`에 **부분 UNIQUE 인덱스**(`round_id WHERE accepted AND NOT revoked`)를 두어 로직이 틀리더라도 DB가 승자 2명을 거부합니다.
3. **판정 기준은 "서버 접수(직렬화) 순서"**. 클라이언트 타임스탬프는 사용하지 않습니다. 네트워크 지연 차이 때문에 실제 손가락 순서와 수십 ms 다를 수 있다는 점은 모든 부저 시스템의 물리적 한계이며, 사회자 화면에 접수 순서와 시간차(+0.035s 등)를 보여줘 박빙 상황을 판단할 수 있게 했습니다.
4. **멱등성**: `(round_id, arm_seq, participant_id)` UNIQUE → 연타·네트워크 재전송은 같은 결과를 돌려받을 뿐 시도가 늘지 않습니다. 클라이언트는 네트워크 오류 시 안전하게 자동 재시도합니다.
5. **round_id 검증**: 부저 요청에는 화면에 보이던 라운드 ID가 실립니다. 이미 끝난(FINISHED) 라운드나 다른 방의 라운드는 `STALE_ROUND`로 거절되어 다음 라운드에 절대 반영되지 않습니다.
6. **Realtime은 전파용일 뿐**: `rooms`, `rounds` 테이블의 변경을 postgres_changes로 받아 즉시 화면에 반영하고, 곧바로 RPC로 서버 상태를 재조회해 **최종 화면은 항상 서버 상태**가 되게 합니다. Realtime이 끊기면 2초 간격 polling으로 자동 전환되고, 3~5초 후 재구독을 시도합니다.

### 인증·보안 구조

| 대상 | 방식 |
| --- | --- |
| 참가자 | 입장 시 256-bit 랜덤 토큰 발급 → 브라우저 localStorage 보관. DB에는 **SHA-256 해시만** 저장(`private.participant_tokens`). 모든 참가자 RPC는 토큰으로 본인을 식별 → 다른 사람 ID로 누르기 불가 (API가 ID를 아예 받지 않음). |
| 사회자 | 비밀번호 bcrypt 해시를 `private.admin_config`에 저장(SQL 편집기에서만 설정). 로그인 시 24시간 세션 토큰 발급, 해시만 저장. 모든 `admin_*` RPC가 첫 줄에서 검증. 5분 내 10회 실패 시 로그인 잠금. |
| 테이블 | 전 테이블 RLS 활성화. anon은 `rooms`, `rounds`만 **SELECT**(Realtime용, 비밀 없음). `participants`, `buzz_attempts`, `private.*`는 접근 불가. INSERT/UPDATE/DELETE 권한 없음. |
| 함수 | 기본 EXECUTE 권한을 모두 회수한 뒤 공개 RPC만 허용 목록으로 부여. `private` 스키마는 API에 노출되지 않음. |
| 클라이언트 번들 | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`(공개용)만 포함. service_role 키·관리자 비밀번호는 어디에도 없음. |

> 참고: `rooms`/`rounds`는 공개 읽기이므로 방 코드·라운드 상태·우승자 닉네임은 누구나 볼 수 있습니다(대형 스크린과 동일한 정보). 참가자 목록·토큰은 공개되지 않습니다.

### 라운드 상태

```
WAITING ──준비──▶ READY ──부저 활성화──▶ ARMED ──첫 부저──▶ LOCKED(승자)
   │                                        │                  │
   └────────────부저 활성화─────────────────┘ └──잠금──▶ LOCKED(승자 없음) ──재활성화──▶ ARMED
다음 문제: 현재 라운드 → FINISHED, 새 라운드 READY 생성
우승 취소: 승자 제거 → LOCKED, 다시 활성화하면 취소된 사람은 그 문제에서 제외(오답 처리)
```

## 2. 로컬 실행

Node.js 20 이상이 필요합니다.

```bash
npm install
# embedded-postgres(테스트용) 바이너리 설치 스크립트 허용 — npm이 경고를 띄운 경우에만
npm approve-scripts @embedded-postgres/darwin-arm64   # 사용 중인 OS 패키지명으로
```

### A. Supabase 없이 바로 체험 (로컬 리허설 백엔드)

실제 PostgreSQL을 로컬에 띄우고 같은 마이그레이션을 적용합니다. Realtime 서버는 없으므로 앱은 **polling 모드**(배지: "연결됨 (폴링)")로 동작합니다.

```bash
npm run local:backend     # 터미널 1 — 관리자 비밀번호: localadmin123
npm run dev:local         # 터미널 2 — http://localhost:5173
```

같은 Wi-Fi의 휴대폰으로도 바로 테스트할 수 있습니다: Vite가 출력하는 `Network:` 주소(예: `http://192.168.0.10:5173`)로 사회자 화면을 열면 QR에도 그 주소가 들어갑니다(RPC 요청은 Vite 개발 서버가 로컬 백엔드로 프록시). 실제 행사 전 최종 리허설은 Realtime까지 확인할 수 있는 B 방법으로 하세요.

### B. Supabase 연결

```bash
cp .env.example .env.local   # 값 입력
npm run dev
```

## 3. Supabase 프로젝트 연결

1. [supabase.com](https://supabase.com)에서 새 프로젝트 생성 (리전: **Northeast Asia (Seoul)** 권장).
2. **SQL Editor** → 마이그레이션 파일을 **이름 순서대로** 하나씩 전체 붙여넣고 Run.
   1. `supabase/migrations/20261024000000_buzzer.sql`
   2. `supabase/migrations/20261028000000_family_sync.sql`
   3. `supabase/migrations/20261031000000_family_match.sql`
   4. `supabase/migrations/20261101000000_family_match_images.sql`
   5. `supabase/migrations/20261102000000_ox_survival.sql`
   6. `supabase/migrations/20261103000000_ox_display.sql`
   **이미 적용한 파일은 건너뛰고 그다음 파일만 실행**하면 됩니다(예: 1~5번을 적용했다면 6번만. 기존 방·참가자·기록 유지). 각 파일은 한 번만 실행하세요(두 번 실행하면 "already exists" 오류).
   (Supabase CLI 사용 시: `supabase link --project-ref <ref>` 후 `supabase db push`)
3. **관리자 비밀번호 설정** — SQL Editor에서 (8자 이상):
   ```sql
   select private.set_admin_password('여기에-강력한-비밀번호');
   ```
   비밀번호를 바꾸면 기존 관리자 세션은 모두 로그아웃됩니다. 이 SQL은 SQL Editor 기록에만 남으며 코드·환경변수에는 들어가지 않습니다.
4. **Realtime 확인**: Database → Publications → `supabase_realtime`에 `rooms`, `rounds`, `sync_rounds`, `family_match_games`, `ox_games`, `ox_stage_moves`가 포함돼 있는지 확인(마이그레이션이 자동 추가).
5. **API 키**: Project Settings → API에서 `Project URL`과 `anon`(또는 publishable) 키를 복사해 `.env.local`/Vercel 환경변수에 입력. **service_role 키는 절대 사용하지 않습니다.**

## 5. 행사 운영 가이드

### 행사 전날
- [ ] Vercel 주소로 `/admin` 로그인 → **새 퀴즈방 만들기** → 방 코드 확인
- [ ] QR 이미지 다운로드 → 테이블 안내문/슬라이드에 삽입 (방 코드는 행사 당일까지 그대로 유지 가능)
- [ ] **테스트 모드** ON → 봇 10~20명 추가 → 부저 활성화 → "봇 동시 부저"로 승자 1명 확인 → 테스트 모드 OFF(봇 자동 삭제)
- [ ] 휴대폰 2~3대(iPhone/Android, Wi-Fi/LTE 섞어서)로 실제 리허설
- [ ] 리허설 후 **관리 → 참가자 전체 초기화** (방 코드·QR 유지, 참가자·기록 삭제)

### 행사 당일 장비
- 사회자 노트북/태블릿: `/admin` (전원 연결, 절전 해제, 소리 켜기)
- 연회장 스크린: 별도 브라우저 창에서 **대형 스크린** 버튼 → `/display/방코드` 를 F11 전체화면. 한 번 클릭하면 효과음이 켜집니다.
- 호텔 Wi-Fi가 불안정하면 사회자 기기는 휴대폰 핫스팟 사용 권장.

### 진행 순서 (문제마다)
1. 문제를 읽기 전 **준비 (R)** → 참가자 화면에 "곧 시작합니다" + 초록 표시
2. 문제를 다 읽은 뒤 **부저 활성화 (A)** → 모든 부저가 빨갛게 바뀌고 시작음
3. 첫 부저가 서버에 접수되면 자동으로 잠기고 모든 화면에 "1등! ○○○"
4. 정답이면 **다음 문제 (N)**
   오답이면 **이번 우승 취소** → **부저 활성화** → 그 사람을 제외하고 다시 경쟁
5. 아무도 못 누르면 **잠금 (L)** 후 다음 문제

키보드 단축키 R / A / L / N 지원 (입력창에 커서가 없을 때).

### 참가자 안내 멘트 예시
> "테이블의 QR을 찍고 닉네임을 쓰면 입장! 빨간 버튼이 되면 누르세요. 아이폰은 **무음 스위치를 끄고**, 화면을 한 번 터치해야 소리가 나요."

### 문제 상황 대처
| 상황 | 대처 |
| --- | --- |
| 참가자가 "연결 끊김" | 자동 재연결됩니다. 오래 지속되면 새로고침 — 같은 닉네임으로 자동 복구 |
| 장난 닉네임 | 참가자 목록에서 **퇴장** (닉네임은 재사용 가능해짐) |
| 박빙 판정 시비 | 중앙의 접수 순서(+0.0xx초)를 근거로 안내 — 서버 접수 순서가 공식 기준 |
| 사회자 브라우저 새로고침/종료 | 다시 `/admin` 접속 시 세션·방 자동 복구 (24시간) |
| 잘못된 우승 기록 | 라운드별 우승 기록에서 **취소** |
| 기록 보관 | **CSV 다운로드** (엑셀 한글 호환) |
| 행사 종료 | **게임 종료** → 모든 화면 "게임 종료" + 개인별 1등 횟수 |

DB 테스트는 `embedded-postgres`로 **실제 PostgreSQL 18 서버**를 띄우고, Supabase와 동일한 `anon`/`authenticated` 롤을 만든 뒤 **운영 마이그레이션 파일을 그대로 적용**합니다. 모든 호출은 `anon` 롤 연결로 수행되어 브라우저와 같은 권한에서 검증합니다. 동시성 테스트는 휴대폰 1대 = DB 연결 1개로 시뮬레이션합니다.

## 7. 알려진 제약

- **판정 공정성**: 서버 접수 순서 기준이므로 LTE와 Wi-Fi 사용자 간 수십 ms 차이가 생길 수 있습니다(모든 네트워크 부저의 공통 한계). 사회자 화면의 시간차로 판단을 돕습니다.
- **iOS**: 무음 모드에서는 Web Audio 소리가 나지 않으며 진동 API가 없습니다. 화면 플래시·애니메이션으로 대체됩니다. 화면 꺼짐 방지(Wake Lock)는 iOS 16.4+에서 동작합니다.
- **테스트 봇**은 생성한 관리자 브라우저 메모리에만 토큰이 있어, 새로고침 후에는 삭제 후 다시 추가해야 합니다.
- `/display`와 `/join`에서 방 코드를 생략하면 가장 최근의 진행 중인 방을 사용합니다.

## 8. FAMILY SYNC MODE (Family Sync Challenge)

가족 2명이 한 팀. 각자 휴대폰으로 같은 **가족 닉네임**을 입력해 가입하고, 시작 신호 후 **10초 안에 한 번씩** 누릅니다. 두 사람의 기록 차이(`sync_gap_ms`)가 가장 작은 팀이 1위입니다.

### 서버 설계

| 항목 | 구현 |
| --- | --- |
| 테이블 | `teams`, `team_members`(slot 1·2), `sync_rounds`, `sync_buzzes` — 기존 테이블은 유지, `rooms.mode`·`participants.kind` 컬럼만 추가 |
| 팀 2명 제한 | 팀 행 잠금 후 빈 slot 배정 + **UNIQUE(team_id, slot), slot ∈ {1,2}** → 동시에 6명이 같은 팀에 가입해도 정확히 2명만 성공 |
| 1인 1회 입력 | **UNIQUE(sync_round_id, participant_id)**. 재전송·연타는 `DUPLICATE`로 응답(멱등) |
| 팀당 최대 2건 | **UNIQUE(sync_round_id, team_id, slot)** |
| 위조 방지 | 클라이언트는 토큰과 round_id만 보냅니다. 팀·참가자는 서버가 토큰에서 찾으므로 다른 팀·다른 사람 이름으로 누를 수 없습니다 |
| 이전 라운드 요청 | 최신 라운드가 아니면 `STALE_ROUND` |
| 10초 제한 | 서버가 `started_at ≤ 수신 시각 ≤ started_at + 10초`를 검사. 시작 전 `TOO_EARLY`(기록 안 함, 다시 누를 수 있음), 마감 후 `TOO_LATE` |
| 자동 종료 | 별도 타이머 없이 조회할 때마다 마감 시각이 지난 라운드를 FINISHED로 바꿉니다. 모든 참가자가 누르면 그 즉시 종료합니다 |
| 부저 모드와 분리 | 부저 RPC는 SYNC 참가자 토큰을 거부하고 SYNC RPC는 부저 토큰을 거부합니다. 부저 닉네임 중복 규칙은 부저 참가자에게만 적용됩니다(예: "아빠"가 여러 가족에 있어도 됨) |
| 비공개 | 브라우저(anon)는 `teams`, `team_members`, `sync_buzzes`를 직접 읽을 수 없습니다. `sync_rounds`(상태·시각만, 이름·기록 없음)만 Realtime용으로 읽을 수 있습니다. 발표 전에는 참가자·대형 스크린 응답에 기록·순위가 들어가지 않으며, 파트너가 눌렀는지도 알려주지 않습니다(신호로 쓰는 것 방지) |

### 시간 측정 — 정밀도와 실제 지연은 다릅니다

- **시작 시각 예약 전파**: 사회자가 시작을 누르면 서버가 `started_at = 지금 + 3초`로 정하고 이 값을 전파합니다. 휴대폰은 RPC 왕복 시간으로 서버 시계와의 오차를 추정해서(가장 빠른 왕복 기준) **같은 서버 시각에 3·2·1 → SYNC!** 가 되도록 맞춥니다. 신호가 늦게 도착한 휴대폰은 카운트다운이 짧아질 뿐, 기준 시각은 모두 같습니다.
- **기록** = `clock_timestamp()`(PostgreSQL이 요청 처리를 시작한 순간, 잠금 대기 이전) − `started_at`. ms 단위로 반올림해 저장하고, **화면에 보이는 값 그대로** 순위를 매깁니다.
- PostgreSQL 타임스탬프의 정밀도는 μs이지만, 기록은 **서버 도착 시각**이라 각 휴대폰의 네트워크 지연(보통 수십~150ms, 순간 변동 수십 ms)이 포함됩니다. 실제 손가락이 닿은 시각과 다를 수 있습니다. 같은 Wi-Fi에 있는 두 휴대폰은 지연이 비슷해서 차이가 상당 부분 상쇄되지만, LTE와 Wi-Fi가 섞이면 수십 ms 차이가 생길 수 있습니다. 근소한 차이는 재미로 보고, 필요하면 재경기하세요.
- 클라이언트 시각은 카운트다운 표시에만 씁니다. 판정과 기록에는 쓰지 않습니다.

### 순위 규칙
- 2명 모두 10초 안에 누른 팀만 순위에 들어갑니다(**완료**). 1명만 누른 팀은 **미완료**, 아무도 안 누른 팀은 **미참여**로 표시합니다.
- 차이가 작은 순으로 정렬합니다. **동점이면 공동 순위**(1, 1, 3위…)로 표시하고, 숨겨진 기준으로 가르지 않습니다. 사회자 화면에 **"n위 동점 재경기"** 버튼이 나타나며, 누르면 해당 팀만 참여하는 새 라운드가 열립니다(다른 팀은 관전).

### 진행 순서
1. 사회자 화면 상단 **게임 모드 → FAMILY SYNC MODE**. 참가자 휴대폰이 자동으로 가족 팀 가입 화면으로 바뀝니다(일반 부저 참가자도 같은 QR로 접속).
2. 가족 2명이 같은 **가족 닉네임**(10자)과 각자 **이름·호칭**(8자)을 입력합니다. 화면에 "파트너를 기다리는 중" → "2명 모두 접속 완료"가 표시됩니다. 사회자 화면에는 팀별 2/2와 접속 상태가 표시됩니다.
3. **준비** → 참가자 "준비하세요!" 표시.
4. **시작** — 응답이 없는 참가자나 파트너가 없는 팀이 있으면 먼저 경고합니다. 3·2·1 뒤 10초 동안 입력을 받습니다(참가자·대형 스크린에는 남은 시간 숫자를 표시하지 않음). 사회자 화면에서는 실시간 입력 인원과 남은 시간을 볼 수 있습니다.
5. 10초가 지나거나 모두 누르면 자동 종료 → 대형 스크린 **"결과 집계 완료"**.
6. **다음 순위 공개**를 누를 때마다 5위 → 4위 → … → 1위 순으로 공개됩니다(6위 이하는 첫 공개 때 함께 표시). 1위가 공개되면 큰 화면 + 컨페티 + 팡파르가 나옵니다. **전체 공개**로 한 번에 공개할 수도 있습니다.
7. **다음 라운드** 또는 동점 재경기를 진행합니다. 결과는 **CSV 다운로드**로 저장할 수 있습니다.

- "대형 스크린에 입력 완료 인원 표시" 체크박스로 대형 스크린에 "입력 완료 n / m명"을 보여줄지 정합니다(기본 꺼짐).
- 가족 닉네임을 잘못 입력한 참가자는 대기 화면 하단의 "가족 닉네임을 잘못 입력했어요"를 눌러 다시 가입할 수 있습니다(진행 중에는 불가). 사회자는 팀 목록에서 **제외**로 빈자리를 만들 수 있습니다.
- **FAMILY SYNC 전체 초기화**는 가족 팀·SYNC 기록만 지우고 부저 참가자·기록은 그대로 둡니다. 가족 팀은 이구동성과 공유하므로 이구동성 점수도 지워지고 새 게임(문항 유지)으로 돌아갑니다. 관리 → **참가자 전체 초기화**는 모두 지웁니다.
- 테스트 모드를 켜면 **SYNC 테스트 봇**(봇 가족 2명씩)을 만들어 실제 `sync_buzz` 경로로 입력해 볼 수 있습니다.

## 9. 가족 이구동성 (FAMILY MATCH)

같은 가족 팀의 두 사람이 각자 휴대폰으로 **A 또는 B**를 고릅니다. 정답은 없고, **두 사람의 선택이 같으면 1점**입니다. 설정한 문항 수(1~10, 기본 10)를 마치면 가족별 누적 점수로 순위를 냅니다.

### 기존 구조 재사용
- 가족 팀은 **FAMILY SYNC와 같은 팀**(`teams`, `team_members`, 가족 참가자 토큰)을 씁니다. 같은 QR·같은 가입 화면이고, 한 번 가입하면 SYNC와 이구동성을 오갈 때 다시 가입할 필요가 없습니다.
- 사회자 인증, 토큰 해시 저장, `SECURITY DEFINER` RPC, RLS, Realtime + polling 동기화, 서버 시계 추정은 기존 방식을 그대로 씁니다. 새 프레임워크·서비스는 추가하지 않았습니다.

### DB (`20261031000000_family_match.sql`)

| 테이블 | 내용 |
| --- | --- |
| `family_match_games` | 방(`room_id`)마다 게임 1, 2, … 상태·문항 수·현재 문항·누적 순위 공개 여부·최종 공개 단계. **Realtime 공개용**(답·점수 없음) |
| `family_match_questions` | 게임별 10개 문항: `question_number`, `story_title`, `story_text`, `question_text`, `option_a`, `option_b`, `duration_seconds`(5~30), `status`, 열림/마감 시각 |
| `family_match_answers` | 참가자 답. **UNIQUE(question_id, participant_id)**, **UNIQUE(question_id, team_id, slot)** → 문항당 1인 1답, 가족당 최대 2답 |
| `family_match_question_results` | 마감 순간 확정된 가족별 판정(두 선택·일치·점수). PK(question_id, team_id) |
| `family_match_results` | 게임 종료 시 최종 순위: 일치 수, 전체 문항 수, 일치율, 순위 |

스펙의 `session_id`는 이 프로젝트의 방(`rooms`)에 해당하므로 `room_id`로 연결했습니다. `rooms.mode`에 `'MATCH'` 값만 추가했고 기존 테이블·함수 동작은 바뀌지 않습니다(가족 가입 허용 모드에 MATCH 추가, 초기화 시 이구동성도 정리).

### 상태와 규칙

```
LOBBY ─문제 준비─▶ QUESTION_READY ─응답 시작─▶ QUESTION_OPEN ─(제한 시간 / 조기 마감)─▶ QUESTION_CLOSED
      ─결과 공개─▶ RESULT_REVEAL ─다음 문제─▶ QUESTION_READY … ─최종 결과 공개─▶ GAME_FINISHED
```

- 모든 상태 전환은 `admin_match_action`(사회자 토큰 필수)만 할 수 있습니다. 요청에 사회자 화면의 게임 ID·현재 문항 번호가 함께 실려서, 더블클릭이나 오래된 화면으로 문항을 건너뛸 수 없습니다(`ROUND_CHANGED`).
- **제한 시간은 서버 시각 기준**: 응답 시작 시 `closes_at = 지금 + 제한 시간`. 서버 수신 시각이 `closes_at` 이후면 `TOO_LATE`. 별도 타이머 없이 조회할 때마다 마감 시각이 지난 문항을 닫습니다.
- **답 변경**: 시간 안에는 몇 번이든 바꿀 수 있고 **마지막 답**이 인정됩니다. 요청마다 증가하는 순번(`p_seq`)을 붙여서, 느린 네트워크에서 예전 요청이 늦게 도착해도 새 답을 덮어쓰지 못합니다(`STALE`). 같은 요청 재전송은 그대로 `ACCEPTED`.
- **마감과 제출이 동시에 일어나도 일관됨**: 답 제출은 문항 행에 공유 잠금, 마감은 배타 잠금을 잡습니다. 마감은 진행 중인 제출이 끝나길 기다렸다가 그 순간의 답으로 판정을 확정하고, 이후 제출은 `CLOSED`가 됩니다. 접수된 답은 반드시 판정에 들어가고, 거절된 답은 절대 들어가지 않습니다(20명 동시 제출 + 마감 경합 테스트).
- **점수**: 두 답이 같으면 1점, 다르거나 한 명이라도 미응답이면 0점. 점수는 판정 행에서 매번 계산하고 더해 가지 않으므로, Realtime 메시지가 중복·역순으로 와도 두 번 계산되지 않습니다.
- **최종 순위**: 일치율 = 일치 문항 수 ÷ 전체 문항 수 × 100. 미응답 문항도 분모에 포함합니다. 동점은 공동 순위(1, 1, 3).
- **문항 다시 시작**: 해당 문항의 답과 판정을 모두 지우고 READY로 되돌립니다. 다른 문항 점수는 그대로입니다.
- **게임 초기화(새 게임)**: 게임 번호를 하나 올려 1번 문항부터 새로 시작합니다(문항 세트·설정 복사). 이전 게임의 답·점수는 별도로 보관되고 섞이지 않습니다.
- **여기서 게임 끝내기**: 시간이 부족할 때 진행한 문항까지만으로 최종 순위를 냅니다(분모 = 진행한 문항 수).
- **동점 결승**: 최종 순위에 동점이 있으면 사회자 화면에 **"n위 동점 → FAMILY SYNC 결승전"** 버튼이 나타납니다. 누르면 FAMILY SYNC 모드로 바뀌고, 동점 가족만 참여하는 SYNC 라운드가 준비됩니다(같은 휴대폰 세션 그대로).

### 공정성·비공개
- 참가자는 **자기 답만** 볼 수 있습니다. 파트너의 답은 사회자가 **결과 공개**를 누른 뒤에만 응답에 포함됩니다.
- 응답 중에는 **사회자 화면에도 A/B 선택이 보이지 않고** 가족별 응답 인원(0/2, 1/2, 2/2)만 보입니다. 마감 후 사회자에게 먼저 상세 결과가 보이고, 공개를 눌러야 참가자·대형 스크린에 표시됩니다.
- 브라우저(anon)는 문항·답·판정·결과 테이블을 직접 읽거나 쓸 수 없습니다. Realtime으로 전파되는 `family_match_games`에는 상태만 있습니다. 답 제출은 Realtime 이벤트를 만들지 않으며, 사회자 화면·대형 스크린은 응답 중 1~1.5초 간격으로 진행 현황을 조회합니다.
- 대형 스크린의 누적 순위(선택)는 **공개된 문항만** 집계하고, 마지막 문항부터는 자동으로 숨겨 최종 발표 전에 순위가 드러나지 않게 합니다.

### 진행 방법 (사회자)
1. 게임 모드 → **가족 이구동성**. 휴대폰이 자동으로 "우리 가족 이구동성" 가입 화면으로 바뀝니다. 이미 SYNC로 가입한 가족은 그대로 이어집니다.
2. 아래 **게임 설정·문항 편집**에서 제목, 전체 문항 수(1~10), 제한 시간(5~30초, "모든 문항에 적용"), 문항 내용과 순서(↑↓)를 고치고 **저장**합니다. 기본 문항은 「사라진 문화상품권 40장을 찾아라!」 10문항입니다. 게임 중에는 아직 시작하지 않은 문항만 수정할 수 있습니다.
3. **문제 준비** → 휴대폰·대형 스크린에 문제와 보기가 표시됩니다(버튼은 아직 꺼짐). 이야기를 읽어 주세요.
4. **응답 시작** → 타이머 시작. 한 명만 들어온 가족이나 응답이 없는 참가자가 있으면 먼저 알려 줍니다. 사회자 화면에 남은 시간과 가족별 응답 인원이 실시간으로 보입니다.
5. 시간이 끝나면 자동 마감(또는 **응답 조기 마감**) → 대형 스크린 "과연 우리 가족의 마음은 통했을까요?". 사회자 화면에는 상세 판정이 먼저 보입니다.
6. **결과 공개** → 대형 스크린에 가족별 `A / A → 일심동체 성공!` 이 차례로 나타나고, 휴대폰에는 내 선택·파트너 선택·점수·누적 점수가 표시됩니다(일치하면 축하 효과, 불일치면 "서로 다른 생각도 재미있어요!").
7. **다음 문제 ▶** 로 3~6 반복. 마지막 문항 뒤에는 **최종 결과 공개**.
8. **다음 순위 공개**를 누를 때마다 3위 → 2위 → 1위 순으로 발표합니다(4위 이하는 첫 발표 때 함께 표시). 1위 발표 시 컨페티와 팡파르. 최종 순위는 **CSV**로 저장할 수 있습니다.

참가자 안내: "가족 두 분이 QR로 들어와 **같은 가족 닉네임**을 입력하세요. 문제가 나오면 상대 답은 보이지 않으니, 우리 가족이라면 뭘 고를지 생각해서 A나 B를 누르세요. 시간 안에는 바꿔도 됩니다!"

### 문항 그림 (대형 스크린)
대형 스크린은 문제 준비·응답 중·응답 마감 화면에서 해당 문항의 그림을 왼쪽에 크게 보여 주고, 결과 공개 화면에서는 같은 그림을 배경에 흐리게 깔아 줍니다.

- 그림은 **문항마다 저장**됩니다(`family_match_questions.image_url`). **게임 설정·문항 편집**의 각 문항 아래 **대형 스크린 그림**에서 고르고 **저장**하세요. 미리보기 썸네일이 함께 보입니다.
  - **밸런스1 ~ 밸런스10**: 앱에 포함된 그림(`public/match/q1.jpg` ~ `q10.jpg`, 프로젝터용으로 최대 1600px)
  - **다른 그림 (웹 주소)**: `https://`로 시작하는 그림 주소(따옴표·괄호·공백은 보안상 거부)
  - **그림 없음**
- 기본 문항은 1번=밸런스1 … 10번=밸런스10으로 연결되어 있고, ↑↓로 순서를 바꾸면 **그림도 문항과 함께 움직입니다**. 새 게임(게임 초기화)에도 그대로 복사됩니다.
- 게임 중에는 아직 시작하지 않은 문항의 그림만 바꿀 수 있습니다(다른 내용과 같은 규칙).
- 앱에 포함된 그림 자체를 바꾸려면 같은 이름으로 파일을 교체하고 다시 배포하면 됩니다. 그림을 불러올 수 없으면 그림 없이 표시됩니다.

테스트 모드를 켜면 **이구동성 테스트 봇**(봇 가족, 약 60% 확률로 같은 답)을 만들어 실제 `match_answer` 경로로 응답해 볼 수 있습니다.

## 10. OX SURVIVAL (구두 출제 OX 서바이벌)

사회자가 문제를 **말로** 내고, 참가자 전원이 휴대폰에서 O 또는 X를 고릅니다. 틀리거나 시간 안에 고르지 못하면 탈락, 최후의 1인이 우승합니다. **문제 문장·해설은 시스템에 저장하지 않습니다.** 시스템은 라운드 번호, 라운드별 정답(사회자가 비공개로 저장), 참가자 응답, 생존 상태만 관리합니다.

### 기존 구조 재사용
- 참가자: 기존 `participants`와 토큰을 그대로 씁니다. **퀴즈 부저 닉네임**으로 들어온 사람과 **가족 팀원**(FAMILY SYNC·이구동성) 모두 각자 개인으로 참가하며, 가족 팀원은 "가족명 호칭"(예: 김가족 아빠)으로 표시됩니다. 새로 오는 사람은 OX 화면에서 닉네임으로 입장합니다.
- 인증·RPC·Realtime·서버 시계·폴링 대체·재연결은 기존 모드와 같은 방식입니다.

### DB (`20261102000000_ox_survival.sql`)
| 테이블 | 내용 | 클라이언트 접근 |
| --- | --- | --- |
| `ox_games` | 게임 상태, 현재 라운드, 제한 시간(기본 10초, 5~30), 최초 참가자 수, 결과(CHAMPION/CO_WINNERS/ENDED) | SELECT만 (Realtime용, 정답 없음) |
| `ox_rounds` | 라운드별 **정답**, 시작·마감·공개 시각, 생존자 수 전/후, O/X 수 | 불가 (RPC만) |
| `ox_players` | 게임 시작 때 확정된 명단, ALIVE/ELIMINATED, 탈락 라운드 | 불가 |
| `ox_answers` | 라운드·참가자당 1행(UNIQUE), 마지막 유효 답 | 불가 |
| `ox_round_results` | 정답 공개 때 고정되는 판정 기록 (라운드+참가자 기본키) | 불가 |

`rooms.mode`에 `OX`가 추가되고 `admin_set_mode`, `admin_reset_room`이 OX를 함께 처리하도록 갱신됩니다. 기존 테이블·데이터는 바뀌지 않습니다.

### 상태와 규칙
```
LOBBY ─게임 시작─▶ ROUND_READY ─(정답 저장)·응답 시작─▶ ANSWERING ─마감/시간 종료─▶ ANSWER_CLOSED
      ─정답 공개─▶ RESULT_REVEALED ─다음 라운드─▶ ROUND_READY (라운드+1)
                 └▶ ROUND_VOID (전원 오답) ─재경기─▶ ROUND_READY (같은 라운드 번호)
      우승자 발표 / 공동 우승 확정 / 게임 종료 ─▶ FINISHED
```
- **게임 시작** 때 지금 접속 중(최근 60초)인 참가자 전원을 ALIVE로 확정합니다(최소 2명). 시작 후 들어온 사람, **닉네임을 바꿔 다시 들어온 사람**은 새 참가자 ID라 명단에 없으므로 관전만 가능합니다. 탈락 상태는 서버에 있어 새로고침·재접속으로 바뀌지 않습니다.
- **정답 저장 전에는 응답 시작 불가**(`ANSWER_REQUIRED`), 응답이 시작되면 정답 변경 불가(`ANSWER_LOCKED`).
- 응답은 생존자만, `ANSWERING` 상태에서 서버 시각 마감 전까지만 받습니다. 시간 안에는 바꿀 수 있고 마지막으로 저장된 답이 인정됩니다(늦게 도착한 예전 요청은 `STALE`로 무시).
- **정답 공개**는 한 트랜잭션에서: 저장된 정답 확인 → 생존자 응답 조회 → 판정 기록 → 오답·미응답 탈락 → 생존자 수 계산 → 결과 공개. 그전에는 아무의 생존 상태도 바뀌지 않습니다.
- **전원 오답**이면 라운드를 무효(`VOID`) 처리합니다. 판정 기록은 남기지만 아무도 탈락하지 않고, 사회자 화면에 "전원 오답 — 재경기 필요"가 뜹니다. **재경기**는 같은 라운드 번호로 새 라운드를 만듭니다.
- **생존자 1명**이면 그 자리에서 우승이 확정되어 다음 라운드를 열 수 없고, **우승자 발표**로 모든 화면에 CHAMPION을 띄웁니다. 2명 이상이면 다음 라운드를 계속하거나 **공동 우승 확정**을 누릅니다.
- 순위: 생존자 1위, 늦게 탈락할수록 높은 순위, 같은 라운드 탈락은 공동 순위(1·2·2 방식).
- **게임 초기화(새 게임)**는 게임 번호를 올려 새로 시작합니다. 이전 게임의 라운드·응답·결과는 그대로 보관됩니다(사회자 화면 "게임 기록").

### 공정성·비공개
- 정답은 `ox_rounds`에만 있고 이 테이블은 클라이언트가 읽을 수 없으며 Realtime에 게시되지 않습니다. 참가자·대형 스크린 RPC는 공개 전 `correct_answer = null`, 생존자 수·O/X 수도 숨깁니다. 정답 저장 시 Realtime으로 나가는 `ox_games` 행에는 "바뀌었다"는 표시(rev)만 있습니다.
- **대형 스크린은 참가자의 O/X 선택을 실시간으로 보여 줍니다**(캐릭터가 해당 진영으로 이동, 아래 '대형 스크린 무대'). 정답은 공개 전까지 어디에도 나오지 않습니다. 참가자 휴대폰에는 다른 사람의 선택·분포가 나오지 않습니다.
- 마감·공개는 라운드 행 배타 잠금, 응답은 공유 잠금 → 마감과 동시에 들어온 응답은 전부 반영되거나 전혀 반영되지 않습니다. 공개를 여러 번 눌러도 한 번만 채점되고(판정 기본키), 더블클릭한 "다음 라운드"는 `ROUND_CHANGED`로 거절됩니다.

### 진행 방법 (사회자)
1. 게임 모드 **OX SURVIVAL** 선택 → 참가자 화면·대형 스크린이 자동 전환. 필요하면 **응답 제한 시간** 변경(다음에 시작하는 라운드부터 적용).
2. 참가 예정자 목록(초록 = 접속 중)을 확인하고 **참가자 확정 · 게임 시작**.
3. 라운드마다: 정답 **O / X 선택 → 정답 저장** → 문제를 말로 읽기 → **응답 시작** → 시간이 지나면 자동 마감(또는 **응답 마감**) → **정답 공개 및 결과 확정**.
4. 결과 화면에서 정답자·탈락자 수와 이름을 확인 → **다음 라운드** / 1명이면 **👑 우승자 발표** / 여러 명이면 **공동 우승 확정** 가능.
5. 전원 오답이면 **재경기**. 언제든 **게임 종료**(응답 중 제외)로 멈출 수 있습니다.

대형 스크린은 아래 '대형 스크린 무대'처럼 캐릭터가 움직이는 게임 무대입니다. **문제 문장은 어디에도 표시하지 않습니다.**

### 대형 스크린 무대 (`20261103000000_ox_display.sql`, `OxDisplay.tsx`, `OxAvatar.tsx`, `oxStage.ts`)
- 무대: 왼쪽 **O ZONE**(파랑, 큰 O 고리) · 가운데 **WAITING ZONE** · 오른쪽 **X ZONE**(빨강, 큰 X), 아래 가운데 퇴장 통로. 위쪽에 ROUND·생존자 수·카운트다운, 아래쪽에 응답 완료 인원·상태·사회자 안내.
- 캐릭터: 참가자마다 작은 사람(둥근 머리·몸통·양팔·양다리·그림자) + 닉네임. 몸 색·피부·머리 모양·소품(산타 모자, 고깔모자, 리본, 안경)은 **참가자 ID에서 만든 고정 키**로 정해져 새로고침해도 같습니다(참가자 ID 자체는 공개하지 않음).
- 움직임(전부 CSS transform/opacity): 대기 중 숨쉬기, 이동 중 팔·다리 교차 걷기와 몸 흔들림, 방향 전환, 도착 시 통통, 정답자 만세 점프, 오답자 고개 숙임(채도↓), 우승자 큰 점프 + 왕관.
- 답을 고르면 그 캐릭터가 0.8~1.5초 동안 해당 진영으로 걸어갑니다. 답을 바꾸면 **지금 있는 자리에서** 반대편으로 다시 걸어가고, 걷는 도중 새 답이 와도 그 자리에서 방향을 바꿉니다(캐릭터는 참가자당 1개, key = 고정 키).
- 자리 배치: 라운드마다 "모두가 한쪽을 골라도 들어가는" 격자를 정해 두고(인원·화면 크기에 따라 열 수와 캐릭터 크기 자동 조절), **자리를 옮긴 캐릭터만** 빈자리를 새로 받습니다. 겹치지 않는 범위에서만 살짝 흔들어 자연스럽게 배치합니다.
- 정답 공개 연출(서버가 확정한 판정만 사용): ① 과연 정답은?(진영 어둡게, 1초) → ② "정답은 O!" + 정답 진영 빛남 + 정답자 환호 → ③ 오답·미응답자 고개 숙임 → 아래 퇴장 통로로 걸어 나가며 사라짐 → ④ "정답 O! · 17명 중 11명 생존! · 6명 탈락!" + 생존자 손 흔들기. 다음 라운드를 누르면 생존자만 가운데로 돌아옵니다.
- 전원 오답(무효): "전원 탈락! 이번 문제는 무효!" → 아무도 퇴장하지 않고 모두 가운데로 모여 "다시 도전!".
- 우승: 우승자가 가운데로 걸어와 커지고 → 왕관이 떨어지고 → 점프·트로피·컨페티 → "OX SURVIVAL CHAMPION! · 닉네임 · 최후의 1인!" (약 8초 후 손 흔들며 유지). 공동 우승은 우승자 모두가 왕관을 쓰고 나란히 섭니다.
- 실시간: 응답이 저장될 때마다 `ox_stage_moves`에 (캐릭터 키, O/X) 한 줄이 기록되고 Realtime으로 대형 스크린에만 전달되어 즉시 걷기 시작합니다(휴대폰은 구독하지 않음). 이어서 서버 상태를 다시 읽어 확정하고, Realtime이 끊기면 응답 중 0.7초 간격 polling으로 따라갑니다.
- 새로고침·재연결: 연출 단계는 서버 시각(공개·종료 시각) 기준이라, 결과 공개 뒤에 새로고침하면 연출을 다시 하지 않고 마지막 상태(생존자만 남은 화면)로 바로 복원됩니다. 화면에 있는 동안 받은 이벤트는 처음부터 끝까지 연출합니다.
- 1920×1080 기준, 1366×768·4K는 비율(vmin·무대 크기 측정)로 맞춥니다. 25명을 넘으면 캐릭터가 작아지고 열이 늘어납니다(약 60명 이상이면 이름이 줄임표로 잘릴 수 있음).

테스트 모드를 켜면 **OX 테스트 봇**(게임 시작 전에 추가, 약 70% 확률로 정답)으로 실제 `ox_answer` 경로를 시험할 수 있습니다.
